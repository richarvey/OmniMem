# OmniMem Development Guide

## What is this?

Self-hosted semantic memory for AI agents, served over MCP. Memories live in five namespaces: episodic (decisions, bugs, patterns), project context (stack, goals, state, work-type domains), knowledge (RSS articles and extracted facts), preferences (prescriptive rules pulled from conversation) and compiled skills (SKILL.md documents distilled from experience, written only through a propose-and-accept gate). Every memory carries a `licence` (own, open, restricted, unknown) and a `provenance` (retrieved, concluded, asserted).

**Version**: 7.0.10 is the latest release, from `v7.0.x` (and `main`, since the 7.0.3 release); `v7.1.x` is the next line, moving the settings panel onto HTTP at `/admin`. OmniMem 7 is a Rust rewrite of the 6.x Python stack (Valkey, FastMCP server, Starlette web UI, RSS worker) as **one binary**: SQLite with exact in-memory vector search, the MCP server, the enrichment worker and RSS scheduler in one process, and a settings panel at `/admin` that replaces the web UI, opened from a tray or menu bar app on the desktop. The 6.x Python lives on the `v6.x` branches only.

**Stack**: Rust (edition 2024, see `rust-version` in `Cargo.toml`), rusqlite (bundled SQLite), ONNX Runtime via `ort` plus `tokenizers` running all-MiniLM-L6-v2 (384-dim), rmcp over streamable HTTP on axum, minijinja for the panel, tao + tray-icon for the desktop app, reqwest (rustls) for the Anthropic API and feeds, feed-rs, keyring.

The working plan and the evidence for each phase is `docs/rust-port-plan.md`; the Mycelium adapter spec is `docs/v7-change-spec.md`. Update the plan's progress table as phases land.

`omnimem-desktop` is outside the workspace's `default-members`, so plain `cargo build` and `cargo test` need no GUI libraries.

## Running locally

```bash
cargo run -p omnimem -- serve                   # MCP at http://127.0.0.1:8765/mcp, data in the desktop app's data folder, or /var/lib/omnimem where the server package is installed: add --db data/omnimem.db to keep it local
cargo run -p omnimem -- import backup.json      # a 6.x dump_to_file backup, re-embedded
OMNIMEM_DB=/tmp/x.db cargo run -p omnimem -- stats
```

Configuration is the 6.x environment variables (see `crates/omnimem-settings/src/configuration.rs` for the catalogue the panel shows). The desktop app reads `omnimem.env` from its data folder and secrets from the OS keychain into `omnimem_core::env`'s overlay at start; `serve` reads the settings file it finds (`OMNIMEM_ENV_FILE`, `/etc/omnimem/omnimem.env`, then the desktop's), and its Configuration page writes secrets into that file (`SettingsFileSecrets`), since a server has no keychain. Sign in to a local `serve` with `omnimem --db <same db> admin-link`. The production 6.x stack on this host holds ports 8080 and 8765, so use another `MCP_PORT` for live checks.

## Tests and checks

```bash
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test
scripts/desktop-check.sh     # desktop crate: clippy, tests and a smoke test under Xvfb, in ci/desktop
scripts/macos-package.sh     # on a Mac: OmniMem.app in a DMG plus a binary tarball, in dist/macos
scripts/linux-package.sh     # anywhere with Docker: the server .deb, .rpm and tarball, and the tray app tarball, for this arch
scripts/windows-package.sh   # anywhere with Docker: the Windows exe cross-built with cargo-xwin and an MSI from wixl, in dist/windows
scripts/flatpak-package.sh   # anywhere with Docker: the tray app as a Flatpak bundle for this arch, installed and smoke-tested in its sandbox
scripts/docker-image.sh      # after linux-package.sh: the server image from the .deb, for this arch, tested (--push, --manifest for CI)
scripts/coverage.sh          # anywhere with Docker: line coverage of the default members, in dist/coverage, with a badge
scripts/security-check.sh    # anywhere with Docker: cargo audit of Cargo.lock and a gitleaks scan of the history
```

- CI is `.forgejo/workflows/build.yml`, on pushes to any branch but `main`, `v7.*` pull requests and `v7.*` tags. The `linux` jobs (`[linux, amd64]` and `[linux, arm64]`) run `scripts/desktop-check.sh --workspace` (format, clippy, tests, then the desktop checks and smoke test), `scripts/linux-package.sh`, `scripts/flatpak-package.sh` (its GNOME SDK, flatpak-builder state and cargo caches in `~/.cache/omnimem-flatpak` on the runner, so only the first run downloads them) and `scripts/docker-image.sh` (a v7 tag also pushes `richarvey/omnimem:<version>-<arch>`, which `release` joins into `<version>`, plus `latest` for a version without a `-`); the `macos` job runs the same checks, `scripts/macos-package.sh` and the smoke test; the `windows` job (`linux`, so either Linux runner) runs `scripts/windows-package.sh`, with no smoke test since nothing there runs Windows. Once all of them pass, `release` publishes every package: a branch push replaces `dev-<branch>`, a tag attaches to its release. Everything uses the Rust version in `ci/desktop/Dockerfile`, so moving the toolchain is that one line. Beside it, `.forgejo/workflows/checks.yml` runs on every branch push (`main` included) and on pull requests into `v7.*` or `main`: `scripts/coverage.sh` (`[linux, arm64]`, report-only, with `coverage-v7.svg` pushed to the `badges` branch from `v7.*` branches) and `scripts/security-check.sh` (`[linux, amd64]`, failing on a RustSec vulnerability or a leaked secret) without gating the packages. It replaced 6.x's `security.yml`, which ran a lone secret scan on `main` with `runs-on: sqcows` and so could land on the Mac, where it failed for want of Node. `[skip ci]` in a commit message skips both workflows; Forgejo doesn't recognise `[skip-ci]`

- The dev host runs out of memory on parallel builds: set `CARGO_BUILD_JOBS=2` and run the desktop check on its own, never alongside another cargo job
- SQLite runs in memory in tests; there are no store fakes, so a fake can't diverge from the real thing
- Golden fixtures pin byte-level contracts with 6.x: reference vectors (`omnimem-embed/tests/fixtures`), skill bodies (`omnimem-engine/tests/fixtures/skills_golden.json`), the OAuth HTTP surface (`omnimem-mcp/tests/fixtures/oauth_golden.json`). The capture scripts beside them need a `v6.7.x` checkout
- Tests that need the real embedding model run only when the Hugging Face cache has it

## Compatibility contract with 6.x

Kept exactly: the 48 6.x tool names, parameters, defaults and result JSON (including `_compact()` dropping empty values); vectors; recall scoring (floor, weak band, experience weight for every outcome but abandoned, temporal boost, reinstate 0.6, fact collapse, ordering); rendered skill bodies byte for byte; backup JSON, skill bundle zips (format v2, reads v1) and `feeds.yml`; every 6.x environment variable except the Valkey, web UI and PyTorch ones.

Deliberately different (each in the CHANGELOG): dead-end warnings in a scoped `recall` and the PreToolUse hook come only from the same project (or from dead ends with no project), where 6.x matched across all of them (`GRAVEYARD_SCOPE=all` restores that); tool descriptions trimmed of their `Args:` blocks; recency declines from day one to 0.9 at `RECENCY_DECAY_DAYS`, so past it the multiplier is 0.1 below 6.x (the floor and weak band read raw similarity, so they don't move with it); an abandoned outcome weighs 1.0, not 0.1; abandonment no longer auto-suppresses; project-namespace hits carry `tags`, which 6.x's project return fields never listed; `briefing` adds an `update_available` object (`current`, `latest`, `url`) when the background update check (`UPDATE_CHECK`, kv key `meta:latest_release`) has found a newer release, and only then; `recall` and `recall_index` results add `similarity` (raw, rounded to 4 places) beside `score`, and a `forget` preview adds a `hint`; a heuristic contradiction link (the maintenance pass, or `check_contradictions` without `use_api`) leaves `updated_at` alone, where 6.x bumped it, and the maintenance pass links the pairs it finds where 6.x only counted them; the panel lists open pairs from every namespace, not episodic alone; extracted facts carry `as_of` and follow their source through deprioritise, archive, forget and reinstate (a transition's result adds `derived_facts`), where 6.x left them active; over MCP `compile_skill(mode="write")` can return `awaiting_approval`, `declined` or `cancelled` (and `proposal_changed`) instead of committing, unless `HUMAN_APPROVAL=agent`; `check_contradictions` takes `mode="resolve"` (with `key_a`, `key_b`, `outcome`, `winner`, `reason`, `retire_loser`; no mode is the 6.x scan) which writes a `resolution` onto the link in both rows and returns `resolved`, or under `HUMAN_APPROVAL=human` `awaiting_approval`, `declined` or `cancelled`, and recall hits carry `resolved_contradictions` and `superseded_by` when a link is settled (their `contradictions` count is of the links still in dispute); the OAuth metadata lists `none` among `token_endpoint_auth_methods_supported`, both metadata documents are also served with a trailing slash and the resource one at the root `/.well-known/oauth-protected-resource`, unknown scopes are dropped at registration and sign-in rather than refused (`register_bad_scope` and `authorize_bad_scope` in the golden fixture are what 6.x sent), and only `/mcp`, `/authorize` and `/oauth/login` check the Origin (discovery, `/register`, `/token` and `/revoke` take the Host check alone, `oauth::host_guard`); recall and `recall_index` hits carry `trust`, a hit can carry `replaces` (superseded memories folded into it), a superseded memory isn't a hit of its own when its winner is found, a rejected one never is, and candidate and disputed memories rank at `TRUST_CANDIDATE_WEIGHT` and `TRUST_DISPUTED_WEIGHT` (accepted ones score as before); `memory_audit` adds a `trust` count and `recall_detail` and `explain_memory` a `trust` field; query expansion without `ANTHROPIC_API_KEY` logs once instead of nothing; a backup may carry a top-level `feeds` list (the reading list), which 6.x ignores and a restore merges into `feeds.yml` by URL, while `dump_to_file` itself still writes memories only; `remember` takes optional `valid_from` and `valid_to`, and `recall` and `recall_index` optional `valid_at` and `known_at` (bi-temporal, `docs/bitemporal.md`), hits carry `valid_from`, `valid_to` and `retired_at` (ISO times) only where a memory has them, and a memory whose `valid_to` has passed ranks at `VALIDITY_EXPIRED_WEIGHT` in an ordinary recall and is left out of the briefing and the skill compiler, which no 6.x memory can be since none has one; a suppressed topic stays out of the briefing and the graveyard (recall's warnings, the hook and `warn_if_abandoned`), and a rejected memory's dead ends don't warn, where 6.x's suppression covered recall alone; `reopened` puts a memory its reopened resolution superseded or rejected back in dispute; `AUDIT_RETENTION_DAYS` defaults to 0 (keep everything); a 49th tool, `end_validity(key, valid_to?, reason?)`, ends a memory's validity without a successor; `explain_memory` and `recall_detail` add `valid_from`, `valid_to`, `recorded_at` and `retired_at` (ISO, ends only where present); `restore_from_file` never raises trust (to `accepted` or out of `rejected`), caps a new extracted fact at `candidate`, and adds `trust_kept` and `trust_capped` to its result when either happened; `remember` adds `may_supersede` (key, content, similarity) when the new memory states a change and a believed neighbour is above `CONTRADICTION_SIMILARITY_THRESHOLD`. `RECALL_EXPERIENCE_SPAN` above 0 makes the experience weight additive (`(weight - 1) × span`) rather than a multiplier; its default, 0, keeps 6.x's scoring exactly. A 6.x import embeds every memory from its text, never trusting a stored vector, which is why a memory 6.x's KNN had lost (a missing or stale vector on the hash) recalls normally here.

Deliberately gone: Valkey, the 6.x web UI and `/metrics` over HTTP, SSE transport, `EMBEDDING_BACKEND=torch`. Over HTTP the binary serves `/mcp`, the OAuth routes, `/healthz` and, from 7.1, the settings panel at `/admin`, nothing else.

## Design rules that still bind

- **Skill compilation is deterministic**: the same sources render a byte-identical body except the `compiled_at` line. No randomness, map-order dependence or extra timestamps in rendering, or every recompile proposes a noise diff. The skill banner still says "(Valkey)" until cut-over for the same reason
- **Skill writes are gated, and a person accepts**: `compile_skill(mode="propose")` stashes the draft; `mode="write"` commits that stash verbatim and refuses if the stored skill changed. Over MCP the agent's `write` is only a request: under `HUMAN_APPROVAL=human` (the default) the MCP layer asks the person through elicitation and commits only on their accept (`commit_approved_skill`, which also checks the draft is the one they were shown), or answers `awaiting_approval` when the client can't be asked. The settings panel's Pending proposals are the other acceptor, through the plain `compile_skill(mode="write")` that no MCP call reaches. The engine stays transport-agnostic: the decision lives in `omnimem-mcp`, and `HUMAN_APPROVAL` (read in `EngineConfig`) is not skill-specific, so the contradiction gate reuses it (each gate reads its own `HUMAN_APPROVAL_SKILLS` or `HUMAN_APPROVAL_CONTRADICTIONS` first, through `skill_approval()` and `contradiction_approval()`; never read `human_approval` directly for a gate) and `omnimem_mcp::ask_human`: `check_contradictions(mode="resolve")` is asked from the async `call_tool` body (`resolve_with_approval`), a client that can't be asked leaves a pending proposal (`propose_resolution`, a kv hash with a week's TTL) for the panel or `omnimem contradictions accept`, and a panel click or a CLI command is itself the approval Experience and graveyard writes stay ungated; that asymmetry is the design
- **Trust is a person's call, apart from what a confirmed contradiction does on its own**: a memory's `trust` (`omnimem_store::trust_of`, the generated column in `schema.rs` spelling the same default) moves only through `crate::trust`. A model-confirmed link disputes both sides (a heuristic one never does, and the v5 migration recognises one by its fixed explanation, `HEURISTIC_LINK_EXPLANATION`), a resolution settles them, and a person confirms, rejects or restores through `Engine::set_trust`, which the panel and the CLI call and no MCP tool does. Don't add a path from MCP to it. `TRUST_ENRICHMENT=accepted` (`EngineConfig::trust_enrichment`) is the one standing exception, and it is a person's setting, read where the enrichment worker writes an extraction in `llm.rs`. `trust_prior` holds what to go back to; a trust change leaves `updated_at` alone and is audited at `lifecycle`
- **Contradiction links are resolved, never deleted**: `link_contradiction` skips a linked pair, so a deleted link would be found again. `Engine::resolve_contradiction` (`resolution.rs`) writes a `resolution` object onto the link in both rows, bumping `updated_at` so a restore can tell it from the unresolved copy; a settled pair (either row says so) is skipped by the briefing, the hook, the panel list, `check_contradictions` and the maintenance pass, and a new reader that lists links must skip it too (`link_is_resolved`)
- **Domains route, they never label memories**: a project's domains narrow which projects a recall searches; memories don't inherit them. An unmatched domain is always reported, and an empty domain and project intersection returns nothing rather than searching everything
- **Licence and provenance are decided at write time and never scored on**. A fact inherits its source's licence and provenance. Reclassifying goes through the lineage stamp, cascades to chunks and extracted facts, and never bumps `updated_at` (the skill compiler reads that as "source changed")
- **Promotion and feed influence feed skills; ordinary knowledge doesn't.** Refs and feed rules bypass the reinforcement gate but never count towards it or bootstrap a skill
- **Settings are read through `omnimem_core::env`**, never `std::env::var` directly, and nothing writes to the process environment (not sound once the keychain has started threads)
- **The audit log is written by the store, in the change's own transaction** (`omnimem-store/src/audit.rs`). `upsert`, `set_fields`, `set_fields_multi`, `set_fields_each`, `delete_many`, suppression's `set_add`/`set_remove` and a restore record themselves; counters, recall logs, caches and migrations don't go through the hook, so a recall never writes a row. Who is calling is a per-thread context (`omnimem_store::enter(Actor, client)`, a guard), and what the engine is doing is an optional `Op` (`omnimem_store::op`) that names the action, level, reason and detail. Both are thread-locals, so they are only valid on one thread across synchronous calls: set them inside `spawn_blocking`, never across an `.await`. A new entry point that writes (a worker, a command) must `enter` an actor, or its rows say `unknown`. Below `AUDIT_LOG=full` no row may hold memory text: the `KEPT` fields in `audit.rs` are the whole list of values shown. A forget erases text from the log too: `delete_many` calls `scrub_forgotten` in its own transaction, which strips every earlier row for the deleted keys down to `KEPT` plus `BOOKKEEPING` (the names a row uses to describe the change, not the memory), at every level. A new detail key an `Op` adds must go in `BOOKKEEPING` if it is bookkeeping, or a forget will scrub it
- **The fail-closed rule**: a non-loopback `MCP_HOST` needs `MCP_AUTH_TOKEN` or OAuth; OAuth switched on but incomplete refuses to start
- **`/admin` opens only with a panel session**: the panel is where a person accepts skills and contradictions and confirms trust, so `omnimem-settings/src/access.rs` never reads `Authorization`, and the panel is merged into `omnimem_mcp::router_with` after the MCP auth layer (so `/mcp`'s token doesn't apply) and inside the Host/Origin guard. Don't add a path where a bearer or OAuth token gets a session. Sessions and sign-in codes are kv strings (`meta:admin:session:` and `meta:admin:code:` plus a SHA-256), a code is single-use because only the request whose `kv_delete` returns true signs in, and every non-GET needs `Sec-Fetch-Site: same-origin` (or a matching `Origin`) on top of the `SameSite=Strict` cookie. Plain HTTP from another machine is refused unless `ADMIN_ALLOW_HTTP`; a request carrying any forwarding header counts as remote unless it says `https`. `ADMIN_PANEL=false` (OmniMem Cloud) doesn't mount it at all
- **OAuth**: refresh tokens rotate with a grace window (`OAUTH_REFRESH_GRACE_SECONDS`) in which the old token replays the same successor pair, which stops claude.ai's concurrent refreshes being signed out. Codes and tokens are stored as SHA-256 hashes; a code is consumed and a token rotated inside one `Store::with_oauth` transaction

## Gotchas

- **Panel routes are panel paths; links add `/admin`**: routes and every `see_other` target are written as `/memories`, the router in `access.rs` strips `ADMIN_ROOT` and forwards a rebuilt request (rebuilt so its own `{*rest}` path parameter doesn't reach the panel's `Path` extractors), and `see_other` puts the prefix on the `Location`. Templates write `{{ admin }}/...` in every `href`, `action`, `src`, `hx-get` and `hx-post`, and in front of URLs handed to them as variables (`base_url`, `prev_url`, `m.url`). `Panel::handle` runs the bare router with no sign-in, for tests only
- **Downloads are attachments** (`files::attachment`): the browser saves them on whichever machine is browsing. Before 7.1 the window wrote them into the Downloads folder because webviews couldn't be trusted to
- **GNOME shows no tray icon without the AppIndicator extension**; the app opens the panel in the browser once the services run, with `model::NO_TRAY` as the panel's notice
- **No Intel Mac build**: `ort`'s `download-binaries` has no ONNX Runtime for `x86_64-apple-darwin`, so the DMG is arm64 only. Its static library is built for macOS 13.4, which is the app's minimum. A Homebrew Rust has only its host target, so cross-target builds need rustup's toolchain first in PATH
- **All three Forgejo runners carry the `sqcows` label** (Linux amd64, Linux arm64 and the Mac), so `runs-on: sqcows` can land on any of them. Use `macos` or `linux` when the platform matters
- **Release builds keep proc macros unstripped** (`[profile.release.build-override] strip = false`): with Rust 1.96 on macOS, `strip = "symbols"` reaching proc-macro dylibs fails the build with E0463 "can't find crate for `zerofrom_derive`" (or `tokio_macros`, whichever comes first). Debug builds never strip, which is why clippy and the tests pass regardless
- **Every push to a branch other than `main` replaces that branch's `dev-<branch>` pre-release** with the macOS and Linux packages (`scripts/forgejo-release.sh --replace`, from the `release` job only). Version tags (`v7.*`, checked against `Cargo.toml`) attach to their own release instead. Publishing stays in that one job after `needs`: a build job that published on its own would race the `--replace` and lose its files
- **Linux builds need glibc 2.38 or newer, and can't be built on anything older than Debian 13**: ort's prebuilt `libonnxruntime.a` calls the `__isoc23_*` functions (glibc 2.38) and needs GCC 14's libstdc++ (`__cxa_call_terminate`), so a Debian 12 build fails to link and a binary from anywhere won't start on Debian 12 or Ubuntu 22.04. `scripts/linux-package.sh` builds both in `ci/desktop`; the headless one with `CXXSTDLIB=static=stdc++` (plus `-L native=` GCC's folder, which rustc doesn't search) in its own target directory, so it needs only glibc, and runs it in `ubuntu:24.04` before packaging
- **Tarballs made on a Mac need `COPYFILE_DISABLE=1` and `--no-xattrs`** (and `--no-mac-metadata` for bsdtar), or they carry `._omnimem` and `._LICENSE` files and Apple xattr headers that macOS's own tar hides from you but every other tar shows
- **Never write `~/.claude.json` from the app**: running Claude Code sessions rewrite it constantly, so a direct edit can lose theirs or have yours lost. The tray's Add to Claude Code only reads it and changes things through `claude mcp add` / `remove`, run with the usual bin folders on PATH because an app launched from Finder doesn't get the shell's. Claude Desktop's config is fine to edit (only it writes the file, at start): `clients.rs` keeps a backup and renames a complete file into place
- **OpenCode's hooks are a plugin that runs `omnimem hook`** (`omnimem-app/src/opencode-plugin.js`, written by `install-hooks --opencode` and the tray's Add hooks to OpenCode): OpenCode has no command hooks, so the plugin sends Claude Code's PreToolUse and SessionStart JSON with OpenCode's own tool names and arguments, which `hook.rs` reads (`OPENCODE_GUARDED`). Keep the plugin's `GUARDED` list and `OPENCODE_GUARDED` the same (a test checks). One file serves both plugin APIs through a single default export, as OpenCode documents: 2.x reads its `id` and `setup()` (`ctx.tool.hook("execute.before")`, where any thrown error becomes a Tool.Error rejecting the call, and `ctx.session.hook("context")`, pushing `{ type: "text", text }`), 1.x from 1.18.29 calls its `server()` (`tool.execute.before`, `experimental.chat.system.transform`, pushing a string). 2.x refuses a file without that default export and 1.x one with an export that isn't a plugin, so add no other export. It runs omnimem by full path, since OpenCode's desktop app has no shell PATH. OpenCode reads `opencode.json` and `opencode.jsonc` (1.x also `config.json`) from `$XDG_CONFIG_HOME/opencode` (or `~/.config/opencode`) on every OS. Add to OpenCode writes `opencode.jsonc` if it exists, else `opencode.json`, never `config.json`; under `mcp.servers` when the file already uses 2.x's form, else under `mcp`, which 2.x still reads and migrates
- **Mistral Vibe's hooks are `hooks.toml` entries running `omnimem hook ... --agent vibe`** (`omnimem-app/src/vibe.rs`, written by `install-hooks --vibe` and the tray's Add hooks to Mistral Vibe): a `pre_tool` guard answering `{"decision": "deny", "reason"}` and a `session_start` briefing answering `hook_specific_output.additional_context` (Vibe 3.1.1+). Vibe's payload names tools in full (`file_system.edit`, `file_system.write_file`, `file_system.bash`, `process.start`, the last being background commands) with Claude Code's argument names; `VIBE_GUARDED` in `hook.rs` and the guard's `match` (short names, `re:edit|write_file|bash|process_start`) must agree (a test checks). OmniMem owns only the hooks named `omnimem-*`. Vibe's MCP servers are `[[mcp_servers]]` in `config.toml` (`$VIBE_HOME`, else `~/.vibe`, on every OS); both files are edited with `toml_edit` so comments survive, after a `.omnimem-backup`. Vibe runs hooks in `/bin/sh`, or on Windows Git Bash else PowerShell, so the program path is written with forward slashes there
- **Codex's hooks are Claude Code's**: same events and `hookSpecificOutput` answers, in `$CODEX_HOME/hooks.json` (else `~/.codex`), so `install-hooks --codex` and the tray's Add hooks to Codex (`omnimem-app/src/codex.rs`) write plain `omnimem hook` / `omnimem hook session-start` with matchers `^(Bash|apply_patch)$` and `^(startup|clear|compact)$`. `apply_patch`'s patch is in `tool_input.command` (OpenCode's in `patchText`). Codex runs a hook only after a person trusts it (its start-up review or `/hooks`), recorded against the hook's hash: never write that trust from OmniMem. No SessionEnd hook: Codex caps it at 3 seconds. Codex's MCP servers are `[mcp_servers.<name>]` tables in `config.toml`, edited with `toml_edit`; hooks run in `sh -lc`, or `cmd.exe /C` on Windows (Codex adds the outer quotes), and share `omnimem_app::shell::hook_base` with Vibe's
- **On Linux a tray icon is "created" even when nothing will show it**: libayatana-appindicator succeeds with no StatusNotifierItem host, which is stock GNOME without the AppIndicator extension, so the app checks the session bus for `org.kde.StatusNotifierWatcher` (`tray_host_running`, through gtk's gio) and, without one, opens the panel with `model::NO_TRAY` set as its notice (`Panel::set_notice`, shown on every page). Linux and Windows trays get `icon::tray`, the compact square `<o>`, since their hosts fit icons into a square
- **The Windows exe needs `DirectML.dll` beside it and the Visual C++ runtime**: ONNX Runtime's Windows build imports both (and `MSVCP140` comes from its C++, so `+crt-static` can't remove the runtime). The MSI ships DirectML (in the target folder it's a symlink into the ort cache that only resolves inside the container) and has a launch condition on HKLM `SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64` `Installed`. `windows-package.sh` fails on any imported DLL outside its allowlist. `wixl` is its own Debian package, not part of `msitools`
- **The Flatpak builds with the network on**: `build-args: --share=network` lets cargo fetch crates and ort fetch ONNX Runtime as on any other build, with cargo's home and target in `/cache/flatpak-cargo` (mounted in with `--filesystem`) so rebuilds are incremental. Fine for a bundle we publish ourselves; Flathub requires offline builds, which means vendoring the crates (`flatpak-cargo-generator`) and ONNX Runtime as an archive source with `ORT_LIB_LOCATION`. The GNOME runtime has no libxdo, which tray-icon's default `muda-libxdo` feature links, so tray-icon is built with `default-features = false, features = ["libappindicator"]` (libxdo only fakes key presses for predefined Copy/Paste menu items, which the tray doesn't use)
- **Inside the Flatpak, the tray icon's file goes in `$XDG_RUNTIME_DIR/app/$FLATPAK_ID`** (`model::flatpak_icon_dir`, through `TrayIconBuilder::with_temp_dir_path`): libayatana hands the tray host a file path, and that folder is the only part of the sandbox the desktop outside can read. Start at login writes `~/.config/autostart/OmniMem.desktop` through the `xdg-config/autostart:create` permission, with `flatpak run --command=omnimem com.squarecows.OmniMem desktop` as its command (`model::login_command`), since `/app/bin` doesn't exist outside. Add to Claude Code is disabled (`model::CODE_IN_FLATPAK`): seeing and running the host's `claude` would take `--talk-name=org.freedesktop.Flatpak`, which is the whole sandbox
- **Installing a Flatpak bundle in a container needs three things the container lacks** (`flatpak-package.sh`): a passwd entry for the calling uid (D-Bus won't start a session without one), a D-Bus session around both `flatpak install` and `flatpak run`, and a system bus, which install asks for parental controls (malcontent). Pointing `DBUS_SYSTEM_BUS_ADDRESS` at the session bus does it: the accounts service is simply absent there, which flatpak takes as "no controls". The error for each is the same unhelpful "Could not connect: No such file or directory"; `flatpak -vv` shows which step it is. Docker Desktop also shows the bind-mounted checkout with another owner, so git needs `safe.directory` (set through `GIT_CONFIG_*` env) before flatpak-builder will read it
- **The macOS signing secrets**: `MACOS_CERTIFICATE` is a base64 `.p12` holding the Developer ID Application key and certificate plus Apple's Developer ID G2 intermediate (so signing doesn't depend on the runner having it), written with `-keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1`: `security import` refuses the AES/PBKDF2 container OpenSSL 3 and 4 write by default with "MAC verification failed". Make the certificate on developer.apple.com from an `openssl req` CSR and pick the **G2 Sub-CA**; "Previous Sub-CA" certificates all end on 1 February 2027. It lasts about 13 months (the current one, `5F6746F9…`, until 20 November 2027) and CI warns 30 days before. CI signs by SHA-1, since a renewal shares its predecessor's name and `codesign` refuses an ambiguous one. The notary key (`5W6DY6U3RC`) is a team App Store Connect key, so it needs `MACOS_NOTARY_ISSUER`. The DMG is notarised and stapled, and the tarball's bare binary notarised too (it can't hold a ticket, so Gatekeeper looks it up online). `fj actions secrets create NAME "$(cat file)"` sets a secret without the value passing through a terminal or a chat
- **The desktop exe is a windowed program on Windows** (`windows_subsystem = "windows"` when built with `desktop`), so a Start menu launch opens no console; `attach_parent_console` lets commands run from a terminal print to it
- **The server packages depend on `ca-certificates`**: reqwest verifies TLS through `rustls-platform-verifier`, which on Linux reads the system CA store, so without it the model download, Claude and every feed fail TLS. Slim images (`debian:13-slim`, the Docker image's base) don't have it, which is also why the `.deb` test installs with `apt-get install ./…deb`, not `dpkg -i`
- **The Docker image is the `.deb` on Debian 13**, built natively per architecture and joined with `docker buildx imagetools create`, so nothing builds under QEMU. Not `docker manifest create`, which refuses a source that is itself an index: debian00 runs Docker's containerd image store, so its half is pushed as one (the image plus a provenance attestation) while the arm64 runner's is a plain manifest. Only `v7.*` tags push, and only a version without a `-` moves `latest`: 6.x's workflow pushed `:latest` on every run, so a manual run on `main` would have overwritten the public images. It runs as uid 1000 (as 6.x did), created before the package so postinst finds the user
- **`install.sh` at the root is not 7's installer**: it's the 6.x one-liner (`curl -fsSL …/raw/branch/main/install.sh | bash`, on omnimem.org and in years of READMEs) kept alive after `main` became 7. It says 7 is out, then runs the 6.7 installer from `v6.7.x` with `OMNIMEM_BRANCH=v6.7.x`, since that installer fetches `docker-compose.hub.yml` from whatever branch it's told. Deleting it breaks every copy of that command
- **Linux package versions use `~` for `-`** (`7.0.2~dev`) so a dev build sorts before its release in dpkg and rpm. Use `tr`, not `${v//-/\~}`: bash 3.2 keeps the backslash, 5.2 doesn't
- **Clippy's `result_large_err` fires on `Result<T, Response>`** (axum's response is at least 128 bytes). Where the error is the response every caller returns at once, it's allowed per function with the reason
- **macOS release builds link clang's runtime** (`omnimem-embed/build.rs`): ONNX Runtime 1.31's CoreML code calls `___isPlatformVersionAtLeast`, which rustc's `-nodefaultlibs` link doesn't supply, and std's copy is dropped by the release profile's LTO, so only a release build failed ("Undefined symbols … ___isPlatformVersionAtLeast"). The build script adds `libclang_rt.osx.a` from `clang -print-resource-dir`
- **ort allows one ONNX Runtime environment per process**, and refuses a second even after the first is dropped, so `omnimem-embed` builds one on first use and every `Embedder::load` shares it (`engine.rs`, `environment()`)
- **A partial index only matches a query that spells its condition**: SQLite can't use one through a bound parameter, so `MemoryFilter::present_any` writes its JSON paths into the SQL (`schema::present_condition`), and `memories_abandoned` is built from the same function. The ensured indexes (`schema::ensured_indexes`) are `IF NOT EXISTS` on every open with no version bump, so a 7.0.x build still opens the store
- **Short-lived processes open the store lazily** (`Store::open_lazy`, used by the hook and the person-only CLI commands): the vector matrix loads on the first search. Every matrix reader calls `sync_external_writes` first, which is what makes this safe; a new reader must too
- **The panel's `context!` is its own macro** (`omnimem-settings/src/lib.rs`): minijinja 3's takes only `Into<Value>` types, so ours wraps every value in `minijinja::value::Serde`, as minijinja 2's `context!` serialised everything. Use it, not `minijinja::context!`, in the panel
- **Panel static files are linked with `?v={{ asset_version }}`** (a hash of every embedded file) and cached for a year under it; anything else revalidates against its ETag. A new file a template links needs the suffix, and the fonts the stylesheet names deliberately go without it, since the preload `href` must match the stylesheet's `url()`
- **Numbers rendered where 6.x output is compared** are formatted to match Python (`str(float)` and friends), not Rust's defaults

## Validation constraints

- Project names: alphanumeric, hyphens, underscores, dots, spaces
- Content: max 50 KB per memory; tags: max 20, each 100 characters or fewer
- Project domains: max 20, same charset as skill domains, aliases resolve
- Skill domains: lowercase kebab-case, 1 to 64 characters of `[a-z0-9._-]`
- `set_licence` and `set_provenance` take at most 200 keys per call
- Key prefixes: `mem:episodic:`, `mem:project:`, `mem:knowledge:`, `mem:preference:`, `mem:skill:`

## Committing

Commit after each meaningful piece of work. The repo lives on Forgejo at `code.squarecows.com` (owner `ric`), pushed over SSH on port 222; the Forgejo MCP points at it for PRs, releases and CI jobs.

**Branch policy**: version lines are developed and released from their own branch (`v7.0.x` here). Cut tags and releases on the version branch. Never merge a version branch into `main` unless Ric asks.

**Releasing** (what CI doesn't do): 7.1 moves the store to schema version 6 (the bi-temporal columns and the `memories_linked` partial index, shared with 7.0.11), which 7.0.10 and older refuse, so its release notes say to back up first. Set the version in `Cargo.toml` (`cargo update -w` for the lock), date the CHANGELOG section, add a `<release>` line to `packaging/flatpak/com.squarecows.OmniMem.metainfo.xml`, and pin the new version in `guides/docker.md`. Tag `v<version>` on the version branch once its build is green. After a full release, on the `pages` branch change the version in `index.html`'s four download buttons, which link straight to the release's files (Forgejo has no latest-download URL for file names that carry the version), and in the four `/download/<platform>` lines of `_redirects`, which keep older links working. `_redirects` also holds short links such as `/source` (GitHub)
